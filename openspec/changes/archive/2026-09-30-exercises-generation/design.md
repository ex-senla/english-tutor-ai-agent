## Контекст

См. `proposal.md` — раздел Why. Актуальное состояние:

- Модуль exercise уже содержит цепочку `GenerateExerciseUseCase` → `ExerciseGenerator` (порт) → `SpringAiExerciseGenerator` (адаптер), подключённую к Spring AI `ChatClient` со структурным выводом (`AiExerciseResponse`).
- `GenerateExerciseCommand` сейчас — `(type, topic, dictionaryId)` — без грамматического правила и числа предложений.
- Поток бота: `AWAITING_EXERCISE_TYPE → AWAITING_EXERCISE_TOPIC → AWAITING_EXERCISE_ANSWER`; единственный текстовый ввод используется как «тема».
- `WordProjection` не содержит статус слова; `Word.getStatus()` вычисляет `NEW` / `IN_PROGRESS` / `LEARNED` из счётчиков повторений.
- AI-провайдер — DeepSeek через стартер Spring AI OpenAI (см. `application.yaml`).

## Цели / Не-цели

**Цели:**

- Сделать генерацию грамматико-ориентированной и соответствующей `examples.MD` для обоих типов упражнений.
- Использовать только слова со статусом `IN_PROGRESS` (roadmap).
- Сохранить существующий паттерн структурного вывода + fallback; без новых провайдеров и зависимостей.

**Не-цели:**

- Ввод уровня CEFR, выбор ученика для упражнения, ограничение слов активным уроком, persistence на JPA/PostgreSQL.
- Переделка алгоритма нормализации строк (strip/lowercase) при сравнении ответов.

## Решения

### 1. Показывать статус слова в `WordProjection`; фильтровать в use case упражнений

Перенести `WordStatus` из `dictionary.domain.word` в `dictionary.api.word` (зеркалит `PartOfSpeech`, который `Word` уже импортирует из `api.word`) и добавить поле `status` в `WordProjection`. `FindWordsService` мапит `Word.getStatus()` в проекцию. `GenerateExerciseUseCase` затем фильтрует проекции по `IN_PROGRESS` перед построением `WordData`.

- **Почему**: политика «какие слова подходят для упражнения» — это поведение модуля exercise (roadmap), а не забота запросов словаря. Оставляя `FindWords` простым источником проекций, мы не раздуваем API словаря фильтрами, специфичными для упражнений.
- **Рассмотренная альтернатива**: добавить `findByDictionaryIdAndStatus(DictionaryId, WordStatus)` в `FindWords`. Отклонено — это переносит политику упражнений в модуль словаря и всё равно требует `WordStatus` в слое API.

### 2. Добавить `grammarRule` в `GenerateExerciseCommand` и в поток бота

`GenerateExerciseCommand` становится `(type, grammarRule, topic, dictionaryId)`. В бота добавляется новое состояние `AWAITING_EXERCISE_GRAMMAR` между `AWAITING_EXERCISE_TYPE` и `AWAITING_EXERCISE_TOPIC`, плюс обработчик, переход и сообщение (`ENTER_EXERCISE_GRAMMAR`). Существующий шаг «темы» остаётся и уточняется как содержательная тема (например, «Animals», «Travelling»).

- **Почему**: ключевой принцип `examples.MD` требует грамматическое правило, чтобы определить, что проверяет упражнение; текущая единственная «тема» смешивает грамматическое правило и содержательную тему, а промпты уже ссылаются на «грамматическую тему от пользователя», которую ни один ввод реально не предоставляет.
- **Рассмотренная альтернатива**: трактовать единственную существующую «тему» как грамматическое правило и отказаться от содержательной темы. Отклонено — текущий пример в промпте («Animals») — содержательная тема, а её удаление теряет привязку к контексту, которую требует `examples.MD`.

### 3. Переписать AI-промпты под `examples.MD`

Оба системных промпта переписываются под правила каждого типа, а сообщение пользователя теперь несёт `grammarRule`, `topic` и список слов `IN_PROGRESS` (слово, часть речи, переводы):

- FILL_IN_THE_BLANK: ровно один `___` на предложение; пропуск проверяет грамматическое правило; ровно один однозначный ответ; целевая лексика — только контекст.
- MULTIPLE_CHOICE: ровно один `___` на предложение; ровно 4 варианта; ровно один правильный; дистракторы — правдоподобные грамматические ошибки целевого правила; правильные ответы распределены по позициям.

Захардкоженные счётчики (`10`, `3`) убираются и заменяются настраиваемым числом предложений.

- **Почему**: текущий промпт MCQ проверяет знание слова (противоречит `examples.MD` §3.1), а оба промпта захардкоживают счётчики, игнорируя конфигурацию.
- **Рассмотренная альтернатива**: few-shot примеры в промпте. Отклонено пока — структурный JSON-вывод плюс явные правила достаточны и дешевле; примеры можно добавить позже без изменения поведения.

### 4. Настраиваемое число предложений через `@ConfigurationProperties`

Новый `ExerciseGenerationProperties`, привязанный к `eta.exercise.generation`, с полем `sentenceCount` (по умолчанию `5`). `SpringAiExerciseGenerator` инжектит его и передаёт счётчик в промпт как точное требование.

- **Почему**: удовлетворяет требованию «число предложений настраивается» без добавления поля в команду, которое пришлось бы собирать в боте.
- **Рассмотренная альтернатива**: добавить `sentenceCount` в команду. Отклонено — это ручка тонкой настройки генерации, а не пользовательский ввод на каждый запрос.

### 5. Валидировать ответы AI; сохранить fallback

После `.entity(AiExerciseResponse.class)` проверять, что список пунктов непуст и у каждого пункта заполнены `sentence` и `correctAnswer`. При любом исключении или невалидном/пустом ответе возвращать существующее fallback-упражнение (помеченное `GENERATED`), чтобы поток не падал.

- **Почему**: сохраняет текущее поведение плавной деградации и ужесточает случай пустого/неполного ответа.

### 6. Структурированная модель ответов

Заменить `AiExerciseResponse(content, expectedAnswer)` на структурную модель, чтобы «упражнение и ответы» были явным JSON, а проверка — по-вопросной:

```java
record AiExerciseResponse(List<AiExerciseItem> items) {}

record AiExerciseItem(
        String sentence,          // предложение/вопрос с ___
        List<String> options,     // пусто для FILL_IN_THE_BLANK, 4 варианта для MULTIPLE_CHOICE
        String correctAnswer      // слово (FILL) или буква варианта (MCQ)
) {}
```

`Exercise`/`ExerciseDto` хранят ожидаемые ответы по-вопросно (`List<String> expectedAnswers`), а `content` для отображения собирается из `items`. `CheckExerciseUseCase` сравнивает ответы пользователя с ожидаемыми по каждому пункту и возвращает фидбек по пунктам.

- **Почему**: сейчас ответ — одна строка через запятую (`"travelled, went"` / `"B, A, C"`), что даёт хрупкое сравнение, отсутствие по-вопросного фидбека и невозможность вывести «json упражнения и ответов» в читаемом виде.
- **Рассмотренная альтернатива**: лёгкий вариант — оставить `content` строкой, а `expectedAnswer` заменить на `List<String> expectedAnswers`. Отклонено как основной путь — без `options` на пункт нельзя корректно отрисовать и проверить MULTIPLE_CHOICE.

## Временный этап — лог вместо показа в чате

Пока отрисовка упражнения и проверка ответа не готовы, поток бота после генерации делает временную заглушку (в коде помечена `// TODO (временно)`):

- выводит JSON упражнения и ответов (структурную модель) в лог;
- в чат отправляет только «упражнение сгенерировано» и возвращается в меню ученика, не переходя в `AWAITING_EXERCISE_ANSWER`.

Позже заглушка заменяется полноценным показом упражнения в чате и включением проверки ответа.

## Риски / Компромиссы

- **Дрейф вывода LLM** (неверное число вариантов, лишние пропуски) → смягчение: строгие правила в промпте; валидация проверяет только непустоту, полная структурная валидация — будущее ужесточение.
- **Перенос `WordStatus` затрагивает импорты в `Word`, `FindWordsService` и тестах** → смягчение: механический перенос, проверяется компиляцией и существующими тестами модулей.
- **Новое состояние бота увеличивает поверхность стейт-машины** → смягчение: точно следовать существующему паттерну handler/transition и проверять готовность через существующий `isReady()`.
- **Грамматическое правило — свободный текст** (опечатки вроде «Past Simpel») → смягчение: допустимо для v1; валидированные/нормализованные грамматические правила — будущее изменение.
